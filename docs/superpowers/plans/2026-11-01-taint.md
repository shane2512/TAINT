# TAINT Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build TAINT, a NEAR contract plus a TEE-hosted agent runtime that gates every value-bearing argument an AI agent proposes by where it came from. Ship it with a reproducible three-agent benchmark that replays the 2026 attacks.

**Architecture:**
- A TypeScript runtime splits the agent in two:
  - A **planner LLM** sees only owner-signed instructions.
  - A **quarantined extractor LLM** turns untrusted content into typed *handles* labeled with their source.
- Proposals carry an argument-provenance map to `taint.near` (Rust, near-sdk). The contract decides `execute`, `pending_cosign` or `reject` per argument, and settles from its own balance.
- The owner co-signs pending proposals with an NEP-366 delegate action, submitted by a small relayer.
- A benchmark runs the same fixtures through a Naive agent, an Allowlist+Caps agent and TAINT.

**Tech Stack:**
- **Contract:** Rust + near-sdk 5.x + cargo-near.
- **Runtime:** Node 20 + TypeScript 5 + vitest + near-api-js 5.x (`@near-js/*`).
- **LLM:** an OpenAI-compatible client (`openai` npm) pointed at NEAR AI Cloud.
- **Web:** Vite + vanilla TS.
- **Build:** GNU make.

**Spec:** [PRD.md](../../../PRD.md). Background: [brainstorm/round2/FINAL.md](../../../brainstorm/round2/FINAL.md).

## Global Constraints

- **Build window:** build 1–14 Nov 2026. Repo public by **2026-11-14 23:59 UTC**. Nothing new starts after D9.
- **Networks:** NEAR **testnet** for everything except `make cosign-demo` and L1, which run on **mainnet with dust amounts**, from a separate dev account.
- **Banners:** every CLI command prints `ATTESTATION STUBBED` when the stub is active (see Task 2). Every benchmark row carries `network` (`testnet`|`mainnet`) and `mode` (`LIVE`|`MOCK`).
- **Baseline name:** the baseline is "Allowlist+Caps". Never call it a simulator.
- **Honest claim:** the README contains this sentence verbatim: "TAINT ties a well-configured allowlist on simple send-to-attacker attacks. It blocks token-choice injection and allows legitimate new tasks without listing them in advance. Inside a mandate it bounds loss rather than preventing it. Trust rests on the TEE, `taint.near`, and the liquidity/age indexer."
- **Baseline freeze:** `baselines/allowlist.json` is frozen with git tag `baseline-frozen` before the first `make replay` LIVE run.
- **Secrets:** env vars only (`.env`, git-ignored). No full-access key remains on the `taint.near` account after deploy.
- **Public text:** no internal scores or win percentages anywhere public. License MIT.
- **Contract defaults:** passed to `new()`. These values are my calls for "low caps"; the PRD fixes none of them.
  - `remember_cap = 1 NEAR`
  - `remember_ttl = 30 days`
  - `payee_cooldown = 24 h`
  - `payee_cooldown_cap = 0.5 NEAR`
  - `global_cap_24h = 5 NEAR`
  - `pause_after_losses = 3`
- **Owner instruction limit:** owner instruction text is at most **280 chars**. Pasted or forwarded content is always an `attachment` (untrusted).
- **Recipients:** NEAR account IDs only. EVM/BTC recipients are out of scope.

**Spec deviations, for the user to confirm:**
1. **R13, Intents for L1.** L1 and the co-sign demo settle as plain NEAR transfers on mainnet. NEAR Intents (1Click) payout is Task 15, a stretch goal. The 1Click deposit address is itself tool output, so gating it needs a pinned-source rule first.
2. **R9, aged named accounts.** Promotion on-chain is **pinned accounts only**. A contract can't read account age. The co-sign UI shows age from an indexer instead.
3. **R8, cooldown scope.** The 24h cooldown applies to payee addresses learned from pinned named accounts. Owner-written "remember" entries skip it, because the owner already signed them; they still get the low cap and the expiry.
4. **Swaps on testnet.** Testnet swaps (F3, L2, L4) go through a `mockdex` contract we deploy, because Intents has no testnet. Every swap row is labeled `mockdex`.

## Review Focus

1. **Attacker text inside the owner instruction.** For example, the owner types "do what this tweet says: …". Instructions over 280 chars are rejected. The CLI and web input put pasted blocks in `attachments`. Test in Task 7.
2. **Amount strings from untrusted text.** Examples: "1.5 NEAR", "1e24", "-3", "max", "all", "1,000", or "1500000000000000000000000" given without a unit. Only an explicit decimal NEAR amount or an integer yocto value parses. "max", "all", negatives and exponents give no handle. Test in Task 6.
3. **Lookalike or invalid account IDs.** Examples: `ACME.near`, `acme.neаr` (Cyrillic а), `acme..near`, and trailing whitespace. The runtime rejects non-ASCII input and lowercases-then-validates against the NEAR account regex before any comparison. The contract's `AccountId` type rejects invalid ones. Tests in Tasks 3 and 6.
4. **Replay or double-settle.** Examples: proposing the same `flow_hash` twice, co-signing an already-executed or expired proposal, or co-signing with the wrong `proposal_hash`. Each must error and move no funds. Tests in Tasks 3 and 5.
5. **Rolling-cap boundary.** Many small transfers that sum past `global_cap_24h` within 24h get rejected. The same transfer after the window passes is allowed. Test in Task 5.

**Policy rules.** The algorithm, from PRD §7:
1. A `Transfer` must have a recipient and no token. A `Swap` must have a token and no recipient. Otherwise → `Reject("malformed")`.
2. A recipient argument that is `Untrusted` is covered by `book_cap(recipient)` or `pinned_payee_cap(recipient)`. Take the larger. If neither applies → pending reason `"recipient from <source>"`.
3. A token argument that is `Untrusted` is covered only by `mandate_allows`. Otherwise → pending reason `"token from <source>"`.
4. An amount argument that is `Untrusted` must be ≤ the cap that covered the recipient (Transfer), or allowed by the mandate (Swap). Otherwise → pending reason `"amount from <source>"`.
5. An `Owner`-class recipient with an amount above that cap is still governed by the rolling cap (Task 5), not by this rule.
6. Any pending reasons → `Pending(reasons)`. Otherwise → `Execute`.

The extractor LLM gets the content and a JSON schema `{accounts: string[], tokens: string[], amounts: string[]}`. Each item goes through the parsers; invalid items are dropped. `recordingKey = "extractor:" + sha256(source+text).slice(0,12)`.
